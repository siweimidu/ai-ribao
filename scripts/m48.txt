为什么需要第三层

GitHub Actions 的 schedule 是尽力而为：官方文档写明高负载会延迟，
排队任务可能被丢弃。实测到 10-25 那一周：

  10-21  配置 3 次，实际 2 次，12:00 时段完全没有运行
  10-25  配置 3 次，实际 2 次

已有两层防护：

  1. 每时段 6 个触发器（每 10 分钟）
  2. watchdog 每 2 小时检查一次

**两层都在同一个会丢事件的调度器上。** 恢复不了一个 GitHub 从未打开的窗口。

════════════════════════════════════════════════════════════════════════
新增：本地 Windows 计划任务

  scripts/external_trigger.ps1
    调 scripts/missing_slots.py 拿 retry= 标记
    缺失就 gh workflow run daily.yml -f force=false

  scripts/register_task.ps1
    注册 AI-Daily-ExternalTrigger
    06:30 / 14:30 / 22:30（每个时段后 2 小时，与 watchdog 的宽限期一致）

关键：**不重复实现时段规则**。判定仍然只有 `missing_slots.py` 一份，
本地脚本只读它的标记。两份规则一定会漂移，而没测试的那份会先错。

幂等

`-f force=false`，走 gate 的 date+slot 判断。
多余的触发是一次空转，不是重复发布。

`StartWhenAvailable`：笔记本 06:30 在睡眠，唤醒后仍会补跑 ——
正是这个任务要解决的失败模式。

脚本里没有硬编码时段规则、注册脚本有三个触发器、
StartWhenAvailable 存在、dispatch 不带 force=true。
