一、git 方案在一天里错了四次

  1. reset --soft FETCH_HEAD
     工作区只有本次调用写的文件，远程有的全显示为删除，commit 把兄弟文件删了

  2. checkout FETCH_HEAD -- .
     修好了删除，但 HEAD 没跟上，push 全部 non-fast-forward（38 张图，38 次被拒）

  3. checkout + reset --soft
     修好了非快进，但 fetch 失败时会继续往下走到 commit，造出孤立提交

  4. 一期两次 store_images（配图、卡片）共用同一份工作副本
     第二次调用会重新指向树

════════════════════════════════════════════════════════════════════════
二、这四个都是「维护本地克隆」的固有属性

换成 GitHub Contents API 之后：

  · 每个文件一次 PUT，按路径定位
  · 没有 index，没有 HEAD，没有 fast-forward
  · 两次调用之间没有共享状态
  · 同样的字节上传两次是 no-op
  · 别人改了分支照样能上传

代价是每个文件一次请求而不是每批一次 —— 一天几十张图，
远在 5000/小时 的认证配额之内。

四、9 项测试重写

断言 API 形态而不是 git 机制：

  · 必须用 api.github.com + contents + base64
  · 必须不含 subprocess / git( / FETCH_HEAD / reset / checkout
  · 必须有 MEDIA_TOKEN
  · 必须报告上传数、已存在数、失败数
  · 相同字节不重复上传
  · 推送失败返回 {}，不留下指向不存在文件的 URL
