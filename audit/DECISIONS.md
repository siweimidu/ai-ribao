## 3. 冲突与不兼容（已识别，必须解决）

### C1 【已消解】07:00 生成 vs 上游源发布时间 —— 会系统性错过当日内容

实测证据（来自 `ai-daily-sources/sources.json` 的真实 `published_at` 与各仓库 workflow cron）：

| 源 | 实际发布/生成时间 | 07:00 时能否拿到"当日"版本 | 10:00 时能否拿到 |
|---|---|---|---|
| juya `daily.juya.uk/rss.xml` | `2026-10-13T09:48:17+08:00` | ❌ 只能拿到 T-1 | ✅ 可以（余量 12 分钟） |
| dailydawn | workflow `cron: '0 0 * * *'` = 08:00 CST | ❌ 只能拿到 T-1 | ✅ 可以 |
| ai-daily-sources | workflow `cron: "2 0 * * *"` = 08:02 CST | ❌ 只能拿到 T-1 | ✅ 可以 |
| daybrief | `cron: "0 23 * * *"` = 07:00 CST | ⚠️ 存在竞态 | ✅ 可以 |
| HN / GitHub Trending / HF / Reddit / 各实验室 RSS | 全天滚动 | ✅ 可以 | ✅ 可以 |

**你的决策：改为北京时间 10:00 单跑**，冲突消解。

**但残留一个新的小风险（必须处理，不能忽略）**：juya 实测 09:48 发布，10:00 只有 **12 分钟余量**。若某天 juya 迟到，或我们的运行被 GitHub 提前触发（罕见但可能），当天就会漏掉它。

**已采纳的缓解措施 —— 关键源等待闸门（Critical-Source Wait Gate）**：
```python
# collect 结束后、进入 analyze 之前
CRITICAL = ["rss:juya", "rss:dailydawn", "rss:hex2077"]   # 当日版必须存在的源
deadline = now + timedelta(minutes=20)
while now < deadline:
    missing = [s for s in CRITICAL if not has_current_day_item(s)]
    if not missing: break
    sleep(120); refetch(missing)      # 只重抓缺失的关键源，不重跑全量
# 超时仍未到 → 不阻塞发布；在 digest.warnings 中显式标注
#   "juya 当日版尚未发布，本期使用 T-1 版本（2026-10-13）"
```
配套的 cron 触发点（避开整点，且互为兜底）：`09:53 / 10:07 / 10:23 / 10:41`，配合幂等闸门 —— 第一个成功发布的生效。


### C2 【中】"保存全部历史" vs 仓库体积膨胀

按中等假设（每日 300 篇文章、每篇正文入库 1.5 KB 摘要+元数据）：
- 纯 JSONL 月度分片：≈ 165 MB/年，可接受（文本，git 增量压缩友好）
- 若把**正文全文**也入库：≈ 3–5 GB/年，**不可接受**

**解决方案**：分层存储 —— 元数据+摘要永久入库；正文全文只保留 30 天滚动的"待分析窗口"，更早的只留指纹与链接。详见 ARCHITECTURE.md §5。

### C3 【中】GPL-3.0 / 无许可证 与"合并六个项目"

`CloudFlare-AI-Insight-Daily` 是 GPL-3.0，`dailydawn`+上游无 LICENSE。若新项目要能自由授权（MIT/Apache），**不能复制这两个仓库的任何源码**。

**解决方案**：新项目以 **MIT** 授权，内核采用 MIT 的 Horizon；只从 GPL/无证仓库吸收 **URL 清单等事实性数据**（事实不受版权保护），对应功能重新实现。详见 §4-L1。

### C4 【低】深度版 + 双语 + 全历史 与"免费额度"的紧张关系

深度版若做中英双语，单日 LLM 调用量翻倍。你的免费额度主力（Groq gpt-oss-120b：**RPD 1,000 / TPD 200K**，官方文档 2026-10-13 核实）在"深度双语"下可能触顶。

**解决方案**：分级用模型 —— 分类/打分/去重用小模型或纯规则；只有摘要与深度分析用大模型；深度版**默认中文**，英文版按需/隔日生成。**请确认（§5-Q2）。**
