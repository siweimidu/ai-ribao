## 判定标准

连续观测 **7 天**后回答：

1. **发布成功率** ≥ 95%？（验收要求）
2. 四个触发点是否足够？若出现过"四个都被丢弃"，需要增加触发点。
3. 实际延迟分布如何？若普遍超过 16 分钟，触发点间隔需要调整。
4. 关键源等待闸门触发过几次？juya 是否稳定在 09:48 前后发布？
5. 有没有出现过"今天完全没有运行"？这是最严重的情况。

## 已知的观测偏差

- 本地时区（Asia/Shanghai）与 runner 时区（UTC）不同，记录实际开始时间时**注明时区**。
- 仓库 60 天无活动会停用定时工作流；本项目每天提交，理论上不会触发，但值得在
  连续观测期结束后隔一周复查一次。

## 首轮观测结论

### 第 0 次：手动触发（2026-10-14 01:46 北京 = 前一日 17:46 UTC）

**这不是调度窗口内的运行**，而是一次刻意的全链路验证：手动 `workflow_dispatch` + `force=true`，
在非调度时段把每一段都跑一遍。

| 阶段 | 耗时 | 结果 | 观测要点 |
|---|---|---|---|
| `gate` | 13s | ✓ | `force` 生效 |
| `collect` | **21m3s** | ✓ | 其中 **20 分钟是等待闸门超时**——见下 |
| `publish` | **12m23s** | ✓ | 采集制品 → L2 → L3 → 分析 → 渲染 → 分发 → 提交 |
| `deploy` | 19s | ✓ | Pages 部署 |

**总耗时 34 分钟，四个 job 全部成功。产物已实际上线：**

| 验证项 | 结果 |
|---|---|
| Pages 首页 `https://siweimidu.github.io/ai-ribao/` | HTTP 200 |
| 单日页面 `2026-10-14.html` | HTTP 200，12,216 字节 |
| RSS `feed/zh.xml` | HTTP 200，**60 个 item** |
| 事实校验 | **0 违规**（231 个事件、231 个链接全部可追溯） |
| 模型用量 | **39 次调用 / 29,920 token**，gemini 28 次 + groq 11 次 |
| 摘要来源 | 40 个事件中 **34 个由模型生成**，6 个降级为规则摘录 |

**幂等闸门也按设计工作了一次。** 本地测试那次已把 2026-10-14 记为 `published`，
所以 GitHub 上这一轮：内容重新生成了（29,920 token 的真实消耗），但**分发被跳过**
（账本里仍是本地那次的 `channels`）。跨环境共享同一本账 —— 一天的日报只会发出一份。

**这次运行发现并修复了一个真实缺陷。**

采集阶段耗时 21 分钟，而不是实测的 17 秒。原因：关键源等待闸门在凌晨 2 点为 juya
的当日版等满了 20 分钟——而 juya 要到 09:48 才发布，那一刻它**根本不存在**。

闸门本身是对的（juya 09:48 发布、调度 10:00，12 分钟余量是巧合不是排期），
但它必须知道「迟到的源」何时才是可能的。已修复为只在调度窗口内启用：

```
run.at - 30min  ->  run.at + 3h     （覆盖 09:53 / 10:07 / 10:23 / 10:41 四个触发点）
```

**同时确认了一件事：闸门超时的行为符合设计。** 运行摘要里出现了明确标注：

> ⚠️ 关键源在等待窗口内仍未发布当日版：`rss:daily-juya-uk`、`rss:hex2077-dev-rss-zh-cn`、
> `jsonfeed:dailydawn-dev`、`rss:ainewslog-com`

四个源**全部被点名**，而不是被静默替换成昨天的内容。这正是"迟到的源不阻塞发布，
但也永远不会被悄悄掩盖"这条设计要求的实际效果。

**首轮还暴露了两个 CI 层面的问题（本地测不出，已修复并验证绿灯）：**

1. **密钥守卫静默失效**：模式里用了 POSIX ERE 不支持的前瞻断言与非捕获组，
   `git grep` 报语法错误退出 2，而 `if git grep` 把非零退出当成"未找到"——
   守卫永远打印 clean、什么都没检查。
2. **PII 守卫命中了测试文件自身**：夹具里写了真实邮箱与 AWS 示例 key。
   守卫在扫描整个仓库，字面量夹具与真实泄露无法区分。

**教训（写进 `scripts/ci_guards.sh`）**：守卫必须在**真实 shell** 下验证，
不能只用 Python 的 `re` 编译一遍就算数——两种引擎的方言不同。

## 首轮暴露的**质量问题**（不是缺陷，但需要决策）

日报头条是「New Apple TV 4K」，模型产出的事实是「Title: New Apple TV 4K」「Points: 153」。
三个原因叠加：

1. **排序只用「独立来源数 + 时间」**，而当天独立来源数全为 0，于是退化成**纯按时间排**——
   高频源（HN 每几分钟一条）必然占满头部，低频高价值的源（实验室博客）永远进不去。
2. **HN 条目本身没有正文**，模型手上只有标题和点数，产不出有信息量的事实。
3. L3 聚类当天降级了（模型不可用），多源事件为 0，第一条排序信号完全失效。

**这是下一轮最该改的地方**：排序需要引入来源权重（`config/daily.yaml` 里已有
`quality.source_weights`，但尚未接入代码），并限制单一源在头部的占比。

## 第二轮：排序质量（2026-10-14 上午）

针对上面「首轮暴露的质量问题」，四个信号替换了原来的排序键。原排序键是
`(-独立来源数, -时间)`，当天独立来源数全为 0 时**退化成纯按时间排**——这就是根因。

新增 `src/aidaily/rank.py` 与 `src/aidaily/entities.py`：

| 信号 | 解决什么 |
|---|---|
| 来源权重 | `quality.source_weights` 在配置里躺了很久，**从未接入代码** |
| 正文实体量 | 只有标题的条目产不出事实，实测就是「Title: …」「Points: 153」 |
| 带下限的新近度 | 指数衰减但保留下限，否则衰减本身又变回纯按时间排 |
| 独立来源佐证 | 两个 feed 承载同一内容时不重复计数（`dedup_group`）|

**实测效果**（同一份真实数据，3882 条 → 窗口内 213 条 → 205 个事件）：

| 指标 | 改动前 | 改动后 |
|---|---|---|
| 前 14 条中同话题条目 | **9 条**（都是 Gemini 4 Argon） | **1 条** |
| 单源最大占比 | **51.7%** | **21.3%** |
| 不同源数 | 10 | 15 |
| 日报条数 | 60 | 60（未被截短） |

同话题那一簇从占据第 1-14 位沉到第 24-29 位。

**过程中修掉五个自己写出的缺陷**（每个都有回归测试）：

1. **回填无视上限** —— 严格轮只填得下约 34 条，回填把剩余 26 个槽位全给了最高产的
   feed，正是上限要防的事。
2. **`stars_today` 让参与度饱和** —— `log10(1500)/3 ≈ 1`，每个 trending 仓库都拿满分，
   九个 GitHub 仓库因此占据前九位。
3. **无日期条目拿到最高新近度 1.0** —— 仓库没有发布时间，却比 6 小时前的实验室公告
   「更新」。**无日期不等于刚刚发布。**
4. **话题惩罚只在第一轮生效** —— 第二轮用 `setdefault` 保留了原始分数，把被惩罚的
   条目**以满分重新塞回**。惩罚机制反而有害，这是最隐蔽的一个。
5. **group 上限变成了日报硬天花板** —— 每个源各自成组 + `max_per_group=3`，
   在约 10 个源的情况下**把 60 槽日报截到 29 条**。我修多样性时把产品砍了一半，
   测试才逼出来。group 只应在多个源**共享**时才生效。

另区分了「同一篇文章」（共享 URL，重罚，属 L2 漏网）与「不同文章报道同一话题」
（轻罚，两个源都该保留）—— 混为一谈时一个真实的第二来源被从第 10 位压到第 50 位。

**一个选择不修的漏判**：有两条 Kylon 的新闻只共享一个实体，没被抓到。
把 `topic_overlap_min` 降到 1 能抓到，但会让任何都提到 Google 的两条新闻被判同话题。
这是精度与召回的取舍，选择保守。

## 第二轮：前端设计（2026-10-14 上午）

把朴素的 `<pre>` 页面换成完整设计，依据 Doubao（设计令牌）与 motion-web（动效规范）。

**设计决策与依据**：

- 弧线选 `editorial` 而非 `broadside` —— 日报是拿来读的，动效花在阅读动作上
- **三种互不相同的段落形态**：信息带（左标题 + 右真实计数）、序号化不等宽事件流、
  等宽数字归档表。规范要求一页至少三种，否则「每段都是标题 + 段落」读作模板
- 配色只用 4 种：主色 `#0065fd` + 中性灰阶。视觉库实测中位数为 4 色，
  且明确禁止紫蓝渐变（最可靠的 AI 味标志）
- 字阶**三轮实测校准**：桌面 5.8×、小桌面 4.3×。规范给的实测中位数是 8×，
  下限 4×（低于 4× 就没有尺度对比）
  - 第一版 80/15 = 5.3× 但 h1 占高 317px（超一屏三分之一）
  - 第二版 58/15 = 3.8× 比例不达标
  - 第三版 正文降到 13px + 展示字 76px，两个约束同时满足
- 中文展示字行高 1.28、字距 -0.01em —— 拉丁面的 1.0/-0.04em 在中文上会闭合字怀

**动效**全部原生 rAF，不引库（实测 9/15 个获奖页面也没用动效库）：
欠阻尼弹簧（替代普通 lerp）、速度耦合、次级果冻、`1-exp(-k·dt)` 帧率无关。
刻意不做：拖尾光标、整卡 hover 抬升、全站统一 fade-up —— 都是闸门点名的。

**真实修掉的问题**：

1. **内容被藏在动效后面**。初版 `.enter{opacity:0}` 写在 CSS 里，观察器没触发时
   前三条事件是隐形的。改成只有 JS 加上 `js-motion` 类才允许隐藏，JS 挂了内容仍在。
   这正是设计规范 B8 闸门的失败模式。
2. 桌面 h1 占高 317px → 147px。
3. 移动端标题 6 行占满首屏 → 4 行，且首条内容进入首屏。

**一次工具欺骗**：`chrome --headless --screenshot` 在字体与布局稳定前就截图，
看起来像「前三条空白」「序号消失」。DOM 实测显示那些元素都在、`opacity=1`、
位置正常。改用 Playwright 截图（`scripts/shots.py`），并新增
`scripts/audit_design.py` 把设计闸门变成可测数字。

**新增 44 个测试**（`tests/unit/test_rank.py` 20 个 + `tests/contract/test_site_design.py` 24 个），
测试总数 323。

## 第三轮：部署路径缺陷与容器条目（2026-10-14 中午）

### 缺陷一：两个 feed 从未被部署

Pages 部署上传 `data/digests/site/`，但 RSS 与 JSON Feed 写在 `data/digests/feed/`。

结果是：**feed 生成完全正确、每个页面都在链接它、线上访问是 404。**
RSS 是给 n8n 的信息流入口——**一个存在但没被提供的 feed 等于没有 feed。**

修法：两个 feed 都写进 `site/feed/`，随站点一起部署。

新增两道 CI 守卫：
- `test_every_linked_path_is_actually_deployed` —— 扫描页面里所有相对链接，
  逐个确认产物里真的存在。修复前它准确报出 `['feed/zh.json', 'feed/zh.xml']`。
- `test_feeds_are_written_into_the_published_directory` —— 在源码层锁住写入位置。

### 缺陷二：纯日期标题占据头条

真实运行的头条第 3 位是「**2026-10-14**」——那是一条日报归档 feed，
**条目标题就是它的发布日期**，正文是整整一天的资讯汇编。

它在每个信号上都赢：正文最长（substance=1.0，容器装着一天的新闻）、
来源权重 1.2、recency 0.955。**任何权重调整都救不了它**，
因为打分衡量的是容器里面的内容，而不是这个条目本身。

新增 `src/aidaily/titles.py`，规则**刻意保持窄**：只有当标题可证明不是标题时才拒绝。
短标题不是证据（「Grok 5」是真标题，四字中文标题很正常），
所以长度**刻意不作为信号**——宽泛的「低信息量」启发式恰好会惩罚这个日报最想要的
那种简短有力的标题。

**降权到 0.15 而非丢弃**：「不得为了架构简洁而擅自删除信息源」是硬约束。

A/B 证据（同一批候选，仅切换 `title_quality`）：容器条目 **第 34 位 → 第 48 位**。

### 一次自己踩的坑：陈旧产物

`--no-deliver` 不拷贝，于是「改了源、量的是旧副本」——**被这个坑了两次**，

`audit_design.py` 先比对字节，陈旧就以退出码 2 拒绝测量；CI 里也有对应断言。

### 合并冲突的处理原则

远程 `c681f54` 是工作流的**真实产物**（25 次调用 / 16407 token），
本地 `--no-llm` 渲染是**占位符**。冲突时的判定依据：

| 内容 | 取谁 | 理由 |
|---|---|---|
| digest / brief / deep / feed | **远程** | 真实 LLM 运行，`llm_usage` 有值 |
| 代码（titles.py / rank.py / 守卫） | **本地** | 修复在上面 |
| 站点 HTML | **重渲染** | 真实数据 + 新代码，两者兼得 |

新增 `scripts/rerender_site.py` 支持从归档 digest 重渲染站点：
改设计不必重跑 LLM（零 token、可复现）。

**注意它忠实重放归档顺序，不重新排序** —— 归档记录的是「当时发布了什么」，
重排等于篡改历史。所以当天的页面里仍会看到纯日期条目，那是历史的一部分；
**修复效果要由新一轮运行来体现**。

### rebase 冲突的一个教训

`git checkout --theirs` 在 **rebase 中语义是颠倒的**：rebase 把 upstream 当作
`ours`（stage 2），把你的提交当作 `theirs`（stage 3）。
我第一次用 `--theirs` 取"远程数据"，实际取回了自己的假数据
（`tokens: None`、200 事件），靠核对 `llm_usage` 才发现。
**结论：rebase 中用 stage 编号（`:2:` / `:3:`）显式指定，不用 `--ours/--theirs`。**
