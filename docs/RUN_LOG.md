真实观测来量化，静态审查得不出结论。四个触发点就是为这两件事设计的，需要数据验证是否够用。

## 判定标准

连续观测 **7 天**后回答：

1. **发布成功率** ≥ 95%？（验收要求）
2. 四个触发点是否足够？若出现过"四个都被丢弃"，需要增加触发点。
3. 实际延迟分布如何？若普遍超过 16 分钟，触发点间隔需要调整。
4. 关键源等待闸门触发过几次？juya 是否稳定在 09:48 前后发布？
5. 有没有出现过"今天完全没有运行"？这是最严重的情况。

## 已知的观测偏差

- 本地时区（Asia/Shanghai）与 runner 时区（UTC）不同，记录实际开始时间时**注明时区**。
- 仓库 60 天无活动会停用定时工作流；本项目每天提交，理论上不会触发，但值得在
  连续观测期结束后隔一周复查一次。

## 首轮观测结论

### 第 0 次：手动触发（2026-10-14 01:46 北京 = 前一日 17:46 UTC）

**这不是调度窗口内的运行**，而是一次刻意的全链路验证：手动 `workflow_dispatch` + `force=true`，
在非调度时段把每一段都跑一遍。

| 阶段 | 耗时 | 结果 | 观测要点 |
|---|---|---|---|
| `gate` | 13s | ✓ | `force` 生效 |
| `collect` | **21m3s** | ✓ | 其中 **20 分钟是等待闸门超时**——见下 |
| `publish` | **12m23s** | ✓ | 采集制品 → L2 → L3 → 分析 → 渲染 → 分发 → 提交 |
| `deploy` | 19s | ✓ | Pages 部署 |

**总耗时 34 分钟，四个 job 全部成功。产物已实际上线：**

| 验证项 | 结果 |
|---|---|
| Pages 首页 `https://siweimidu.github.io/ai-ribao/` | HTTP 200 |
| 单日页面 `2026-10-14.html` | HTTP 200，12,216 字节 |
| RSS `feed/zh.xml` | HTTP 200，**60 个 item** |
| 事实校验 | **0 违规**（231 个事件、231 个链接全部可追溯） |
| 模型用量 | **39 次调用 / 29,920 token**，gemini 28 次 + groq 11 次 |
| 摘要来源 | 40 个事件中 **34 个由模型生成**，6 个降级为规则摘录 |

**幂等闸门也按设计工作了一次。** 本地测试那次已把 2026-10-14 记为 `published`，
所以 GitHub 上这一轮：内容重新生成了（29,920 token 的真实消耗），但**分发被跳过**
（账本里仍是本地那次的 `channels`）。跨环境共享同一本账 —— 一天的日报只会发出一份。

**这次运行发现并修复了一个真实缺陷。**

采集阶段耗时 21 分钟，而不是实测的 17 秒。原因：关键源等待闸门在凌晨 2 点为 juya
的当日版等满了 20 分钟——而 juya 要到 09:48 才发布，那一刻它**根本不存在**。

闸门本身是对的（juya 09:48 发布、调度 10:00，12 分钟余量是巧合不是排期），
但它必须知道「迟到的源」何时才是可能的。已修复为只在调度窗口内启用：

```
run.at - 30min  ->  run.at + 3h     （覆盖 09:53 / 10:07 / 10:23 / 10:41 四个触发点）
```

**同时确认了一件事：闸门超时的行为符合设计。** 运行摘要里出现了明确标注：

> ⚠️ 关键源在等待窗口内仍未发布当日版：`rss:daily-juya-uk`、`rss:hex2077-dev-rss-zh-cn`、
> `jsonfeed:dailydawn-dev`、`rss:ainewslog-com`

四个源**全部被点名**，而不是被静默替换成昨天的内容。这正是"迟到的源不阻塞发布，
但也永远不会被悄悄掩盖"这条设计要求的实际效果。

**首轮还暴露了两个 CI 层面的问题（本地测不出，已修复并验证绿灯）：**

1. **密钥守卫静默失效**：模式里用了 POSIX ERE 不支持的前瞻断言与非捕获组，
   `git grep` 报语法错误退出 2，而 `if git grep` 把非零退出当成"未找到"——
   守卫永远打印 clean、什么都没检查。
2. **PII 守卫命中了测试文件自身**：夹具里写了真实邮箱与 AWS 示例 key。
   守卫在扫描整个仓库，字面量夹具与真实泄露无法区分。

**教训（写进 `scripts/ci_guards.sh`）**：守卫必须在**真实 shell** 下验证，
不能只用 Python 的 `re` 编译一遍就算数——两种引擎的方言不同。

## 首轮暴露的**质量问题**（不是缺陷，但需要决策）

日报头条是「New Apple TV 4K」，模型产出的事实是「Title: New Apple TV 4K」「Points: 153」。
三个原因叠加：

1. **排序只用「独立来源数 + 时间」**，而当天独立来源数全为 0，于是退化成**纯按时间排**——
   高频源（HN 每几分钟一条）必然占满头部，低频高价值的源（实验室博客）永远进不去。
2. **HN 条目本身没有正文**，模型手上只有标题和点数，产不出有信息量的事实。
3. L3 聚类当天降级了（模型不可用），多源事件为 0，第一条排序信号完全失效。

**这是下一轮最该改的地方**：排序需要引入来源权重（`config/daily.yaml` 里已有
`quality.source_weights`，但尚未接入代码），并限制单一源在头部的占比。
